# H2 data: does θ track received volume net of intent?

Generated by `scripts/run_flooding.py` on 2026-10-21, then summarised:

    python scripts/run_flooding.py            # ~14 min, writes panel.parquet, cells.csv, coefficients.csv
    python scripts/summarise_flooding.py      # writes the three summary_* / decomposition files

`python scripts/run_flooding.py --refit` re-runs the regressions on an existing panel without
simulating.

## Design

NCF arm, N = 1000, φ = 0.02, 20 epochs via `run(20)` (no turnover), seeds 42, 43, 44, crossed:

| factor | levels | why |
|---|---|---|
| `ncf.top_k` | 20, 40 | scales received volume; moves the gate and the NCF lists too, so it is not a pure volume knob |
| `hypergamy.signal_cost` | 0, 0.05, 1.0 | 0.05 is open and separating; 1.0 closes after epoch 0 and is kept to show it |
| `hypergamy.flooding_weight` | 0, 0.05, 0.2 | 0 is the shipped rule |

`V` is the count of label-1 swipe-log rows received (column 1 is the receiver), `τ̄` the mean
`intent` of their proposers, `V/V̄` volume over its side mean in that epoch. A closed epoch (no
proposals at all) has no `V̄` and is excluded from the regressions and from the cell means;
`n_open_epochs` and `n_open_late` report how many were left.

## Files

| file | contents |
|---|---|
| `panel.parquet` | one row per (cell, seed, epoch, agent). **Not tracked** (~20 MB); regenerate |
| `cells.csv` | per (cell, seed): open epochs, realised volume and intent, who proposed, gate share, mean Δθ |
| `coefficients.csv` | per (cell, seed, side, window, model): OLS coefficients and standard errors |
| `summary_cells.csv`, `summary_coefficients.csv` | mean and sd of the above over seeds |
| `decomposition.csv` | the flooding term's two factors and its size, acceptor side, open late epochs |

## Models

`net` is Δθ on `V/V̄` alone. The others control for the yield step's own term with
`θ·1[reached]` and `1[reached]`, where reached means one or more deferred-acceptance proposals:
the step skips everyone else, and for acceptors that is most agents. `interaction` adds
`(V/V̄ − 1)(1 − τ̄)`, the flooding term's own shape, whose coefficient is `w` by construction. It
is a check that the rule is implemented, not evidence for H2.

Results and their reading are in THESIS.md (H2) and THEORY.md §3.

## Thread count

**24, and verified to be immaterial here; the directory does not regenerate regardless.**
This directory predates `ncf.num_threads`, so its run took whatever count torch read
from the machine, and the development machine reports 24. But re-running the
`k=20, c=0, w=0, seed 42` cell on 2026-10-25 gives the same `mean_dtheta_W` at 1
thread and at 24 (`-0.03661036` either way), and neither matches the committed
`-0.03620378`. A run built from the commit that produced this directory (`1a075c3`)
gives that same `-0.03661036` at both counts too. So the difference is **not** the
thread count: it comes from code that changed after these cells were generated, not
from the reduction order.

That matters for how the numbers should be read. The volume column at the shipped
regime reproduces (`mean_V_W` matched to four decimals at `admissible_fraction: 0.02`
but not at 0.2, so that column is sensitive to the gate too), while the θ-update
columns do not (`mean_dtheta_W` and `n_matched_mean` both move), which is what a
change in the matching or scoring path would do. The file is therefore a record of
what was run on 2026-10-22 and is not a fixture a current checkout regenerates.
Nothing in the repository claims otherwise for this directory, and
`docs/INTERFACES.md` §3.1(c) is the general statement.

The thread count matters only for the `ncf` arm, which is the arm this whole design
uses.
